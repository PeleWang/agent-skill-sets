# 失败会话诊断

使用用户提供或明确授权查看的原始要求、第一次的答复、用户的纠正意见和可以接受的结果。缺少材料时注明哪些情况还不清楚；如果要求是后来才加的，不用新要求倒推第一次的答复一定有错。

1. 说清哪里出了问题：只引用最必要的证据，指出按当时能看到的要求，本来应当得到什么、实际得到了什么。优先找出最早出现、能解释后来为何返工的偏差。
2. 区分是缺少背景、目标或验收条件不清、规则互相冲突、工具或权限不够、执行时没有遵守现有规则，还是自检没发现问题。只指出有证据支持的原因；有多种解释都说得通时，提出一个简便的办法来验证是哪一种。
3. 改动要落在合适的地方：只与当前任务有关的信息留在该任务中；某个流程反复出现同类问题时，才考虑修改技能；工具出错或没有遵守已有规则时，优先修正执行或验收中出问题的环节，不反复加指令。展示打算修改的文字或检查要求，只提出必要的改动，不擅自保存。
4. 给出一个能查出原问题的验收条件，再给一个未用于制定改动方案的类似案例，避免改动只对原案例有效。说明还没有运行测试，还是已经验证，不把建议当成修复结果。

交付：**预期与实际的对照、证据和可能的根本原因、最小改动、原案例和类似案例的验收条件、有待批准的事项**。默认不保存整份原始日志。
