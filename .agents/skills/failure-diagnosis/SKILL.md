# 失败会话诊断

使用用户给出或明确授权查看的原始要求、首次输出、用户纠正和可接受结果。材料缺失时标记未知；如果后来才增加要求，不用新要求倒推首次输出必然错误。

1. 对齐失败点：引用最短的相关证据，指出对于当时可见的要求，预期和实际分别是什么。优先找最早出现、能解释下游返工的偏差。
2. 区分缺上下文、目标或验收条件不清、规则冲突、工具或权限不到位、执行未按已有规则、自检失效。只说证据支撑的原因；多个解释都可行时给出一个区分它们的小验证。
3. 将改动放在它应在的地方：任务特有信息留在该任务；反复出现的特定流程问题才考虑改 Skill；工具失败或违反已有规则时，优先修相应执行或验收，不重复堆指令。展示拟改文字或检查，只提最小必要改动，不擅自保存。
4. 给出一个能捕获原失败的通过条件，再给一个未用于拟定改动的变体，防止只修一个样本。说明尚未运行还是已验证，不把建议当成修复结果。

交付：**预期 vs. 实际、证据与可能根因、最小改动、原案例和变体验收条件、待批准事项**。不将整份原始日志默认归档。
