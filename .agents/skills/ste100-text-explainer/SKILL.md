# STE100 Text Explainer

用 ASD-STE100 写作原则解释需要理解的内容。保留顺序：**先组织英文解释，再忠实翻译成中文**。默认直接在聊天窗口交付完整中文解释，不要求创建网页或其他文件。

## 触发与范围

不限主题。只要完整、清楚地解释用户所需内容需要超过三句话，就默认采用本 skill 的写作方法，无须用户明确调用。

按内容所需的解释深度判断，不按最终回复恰好写了几句话判断。不要通过堆成长句、省略必要条件或刻意拆句改变触发判断。三句话以内能解释清楚的内容直接简洁回答，不强制执行英文草稿与翻译流程；用户明确调用本 skill 时，无论篇幅都采用。

三句话的阈值只决定是否采用写作方法，不限制最终回复的篇幅，也不把非解释任务改成解释任务。执行任务时，所需的较长说明同样采用此风格，继续完成用户授权的工作。

保持用户当前问题的范围，按所需深度和篇幅回答。用户明确要求其他语言、格式或只要一句话时，以该要求为准。本 skill 不把“解释代码”变成代码修改，也不把“制订计划”变成执行计划。

## 1. 确定内容与证据

沿用已知的读者、目标、深度和提纲。缺少非关键偏好时采用合理默认并简短说明；关键输入影响结论时先确认。若适用的用户指令要求提纲确认，应在正文前完成；已有明确提纲或确认时不要重复询问。

读取用户提供的原论文、代码、数据或规则。需要外部来源时优先使用原论文和官方文档，保留直接来源链接及版本、日期或实验条件。区分来源事实、推断、假设和模拟数值。

数据分析从实际输入计算结果。代码演示依据已核对的执行轨迹或明确标注的模拟。比较方案时给出条件和取舍。计划推演标明工期、资源和依赖的假设。没有现实输入时，可以制作明确标注的教学示例，不能将其展示为用户的真实数据。

## 2. 完成 ASD-STE100 英文解释

先组织英文正文。英文草稿无需展示或保存为文件。围绕用户要理解的关系、过程或判断展开，不使用固定的论文模板覆盖其他场景。

采用 [ASD-STE100 官方标准](https://www.asd-ste100.org/STE_downloads.html) 的写作原则。可用已有合法副本或官方可访问资料核对相关规则和词表。至少执行这些可检查的约束：

- 描述性句子最多 25 个英文单词；操作指令最多 20 个。
- 一个句子表达一个核心意思。一个段落讨论一个主题，最多六句。
- 使用主动、明确的表达和简单时态。避免连续进行时和不必要的名词串。
- 同一概念使用同一术语。遵守批准词汇的词性、含义，以及 technical nouns / technical verbs 的使用规则。
- 正文不用分号。该约束不限制代码的语法。
- 技术名词保留必要的精度，并在正文中定义。不能为缩短句子删去影响理解的条件。

未完成全部规则和批准词表核查时，在回复中简短注明采用 ASD-STE100 写作原则、未验证完整合规性。不要声称认证合规。ASD-STE100 是英语标准，后续中文译文不声称符合该英语标准。

## 3. 忠实翻译成中文，保留英文名称

英文解释完成后，再逐段翻译正文和标题。保留英文版的信息、顺序、条件、公式和例子；不能用重新生成一篇中文解释代替翻译。用户要求英文回答时，直接交付英文解释；要求其他语言时遵从用户。

- 按原句的意思选用中文表达，不逐词硬译。保留句子结构：不拆句、不并句，不改变分句之间的主从、条件、因果或转折关系。用词、搭配和句内语序可以按中文习惯调整。
- 用中文里已有的说法和通行的技术术语，不自造短语。不要因为词偏正式就换掉，先看它在整句里是否自然。「衡量效果」没问题，但「衡量效果看……」应先说清楚是什么的效果；「未参与制定改动方案的案例」应写成「没用来制定改动方案的案例」，免得把案例写成了制定方案的人。
- 先单独通读中文，检查谁在做什么、动词和宾语是否搭配、并列项是否一致，以及读者能否看懂指代。「版本 B」这类只有知道前情才懂的说法，能从原文确认指什么，就把它说清楚，不自行补充或删减信息。再逐句对照英文，核对结构和意思有没有变。

下列内容保留英文原文，即使已有中文译名：

- 论文、文章和作品的正式标题。
- 作者用英文命名或提出的概念、方法、架构、算法等名称。
- 仅有英文表达或没有可靠中文对应的术语。
- API、代码标识符、公式符号、数据字段、专有名称及缩写。

例如保留 `Attention Is All You Need`、`Transformer`、`Scaled Dot-Product Attention` 和 `Multi-Head Attention`。普通说明、通用名词和操作文案使用中文。依照英文正文翻译术语的定义，不额外改写或添加解释。技术名词的命名来源不明时保留其英文拼写，不声称该论文首次发明它。

原文例子、代码、数据值中的英文按例子的意义保留。不要翻译代码标识符或更改代码逻辑。

## 4. 核对与交付

检查关键事实与来源一致，英文名称、数值、公式和中文译文没有遗漏或改变含义。核对中英文的章节、段落和示例对应关系。

有数值计算时核对结果。有代码、流程或规则说明时，核对影响结论的条件和执行步骤。根据实际内容验证，不为纯文字解释启动浏览器或创建交互演示。

默认在最终回复中直接给出完整解释，使用普通文字和必要的 Markdown。先给核心结论，再说明机制、条件、证据或例子；按内容需要使用列表、表格、公式和代码块，不套用固定结构。不以文件链接、截图或 HTML 代码块代替正文，也不自动输出中英双语或对照版本。

保留必要来源、假设和实际限制。用户未要求文件或其他产物时，不创建 HTML、启动本地服务器或另存文档；用户明确要求时按指定格式交付，继续保留语言和证据约束。

遵守当前文件权限和用户授权。用户没有要求时，不发布内容、不上传数据、不向他人发送文件。
